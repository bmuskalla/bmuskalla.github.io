GOTOken: An Inference Engine in QBasic

September 13, 2026 · 8 min read
qbasicllminferencefrom scratch

Running SmolLM2-135M with an inference engine written entirely in QBasic. I wrote it to find out how much of inference I understood, in the language I fell in love with first.

Why BASIC?

My first line of code was a cheat. My father, a civil engineer by training, was working at his PC one day when he opened QBasic for me, loaded NIBBLES.BAS, and let me play, mostly so he could get some work done. Nibbles is the original snake game, for anyone under 40. Somewhere in that file is a factor that makes the snake faster with every level, and the first change I ever made to a program was to turn it down so the later levels stayed playable. The next thing I remember is typing up pages of programs from books, with the delight of watching text turn into execution.

Decades later I wanted to see how far QBasic can be stretched. GOTOken is an inference engine for SmolLM2-135M, a small model with the Llama architecture, written in BASIC and compiled with QB64. It reads the three HuggingFace checkpoint files directly, config.json, model.safetensors, and tokenizer.json, and produces the same tokens that transformers produces from the same prompt. No Python, no C, no numpy, no JSON library. About 1,500 lines of BASIC.

BASIC also turned out to be a good place to find out what you understand, because it hides nothing. If a matrix gets multiplied, a loop in the source multiplies it. Every concept I thought I understood had to become a FOR loop, and every concept I did not understand became a loop that produced the wrong number. That sorts the two faster than any amount of reading.

Two maps guided the work. Andrej Karpathy’s llama2.c is the single C file that runs a Llama model with a for loop and a checkpoint, and the BASIC maps almost one to one onto its run.c, with pointers replaced by integer offsets into one flat SINGLE array. Sebastian Raschka’s Build a Large Language Model (From Scratch) walks through the same architecture one component at a time, and is where the habit of checking each piece before adding the next came from. Every number in this post comes from the commit log of the repository, where the check that produced it sits next to the code.

Eight Steps, Each Checked Against the Real Model

What made this a learning project instead of a debugging project was the order of work. I was driving to learn, and coding agents implemented a lot of the details, so the discipline had to live in the plan rather than in my typing. We did not write the engine and then see whether it worked. It grew in eight steps, and after each step a Python script asked the real model for the same numbers and compared them with the BASIC output. Call that script the oracle. Nothing was added until the previous piece matched. Table 1 lists the steps and what each comparison proved.

Step Added to the engine What the oracle compared Result
1 Loader: all weights into one flat array First and last five floats against the checkpoint Byte for byte
2 Embedding row and the tied output head Logits for one token against a float64 reference Within 4e-6, same top five
3 RMSNorm and MatMul on layer 0 Every output against float64 Within 1e-5 relative
4 One full transformer layer over a sequence A forward hook on the HuggingFace model Max error 1.5e-5
5 All 30 layers and greedy decoding Tokens from model.generate 8 of 8 on “The cat sat on the”
6 KV cache Raw fp32 bits of every chosen logit against step 5 Bit-identical
7 Byte-level BPE tokenizer Token ids for 2,060 strings against HuggingFace 2,060 of 2,060
8 Sampler: temperature, top-k, top-p Seeded draws against a numpy reimplementation Same coins, 8 of 8 tokens

Table 1. The eight steps and what the oracle compared after each one

Step 3 taught me the thing I most needed to unlearn. I had assumed that “correct” meant the same bits as PyTorch. The oracle replayed my BASIC loop in fp32, with the same rounding order, and matched all 576 outputs of the query projection bit for bit. A replay using fused multiply-add matched 243 of them. PyTorch’s own matmul, through BLAS, matched 61. Three correct implementations, three sets of bits. Bit equality across implementations is not a goal; it is an accident of rounding order.

What matters instead is whether the error stays below what the next decision needs. In step 5 the oracle printed, for every generated token, the margin between the top logit and the second. The smallest margin was 0.19. The largest drift from the reference was 1.7e-5. The greedy choice had roughly ten thousand times the headroom it needed, and that ratio, not the bits, is what let me trust the tokens.

What One Token Costs

The whole engine, measured in arithmetic, is this loop:

' xout(d) = W(d, n) * x(n), W stored row-major at w(woff).
' run.c's matmul(xout, x, w, n, d), float* replaced by an offset.
SUB MatMul (xout() AS SINGLE, x() AS SINGLE, woff AS LONG, _
            n AS LONG, d AS LONG)
    DIM i AS LONG, j AS LONG, rowStart AS LONG, acc AS SINGLE
    FOR i = 0 TO d - 1
        rowStart = woff + i * n
        acc = 0
        FOR j = 0 TO n - 1
            acc = acc + w(rowStart + j) * x(j)
        NEXT
        xout(i) = acc
    NEXT
END SUB

Every projection in every layer, and the final multiplication against the vocabulary, goes through it. SmolLM2-135M has 134.5 million weights, and one forward pass touches nearly all of them once, so a token costs about 134 million multiply-adds in a triple loop of unoptimized BASIC. QB64 compiles to C++ and I passed no optimization flags. The result is about one token per second, after four seconds of loading, in 1.1 GB of memory, because the engine holds the weights as fp32 while the checkpoint ships them as bf16 in 270 MB.

The KV cache was the concept I understood least going in, and the one where the oracle earned its keep. Without it, producing the token at step s means running the forward pass over the whole prompt plus s tokens again. For a five-token prompt and eight new tokens that is 68 forward passes and 65.3 seconds. The cache rests on one fact: the key and value rows attention writes for position t depend only on tokens 0 to t, which never change, so a row once written is final. Forward the prompt once, then forward only the new token at its own position. Same rows, same bits, 12 forward passes, 11.5 seconds. Figure 1 shows the two curves side by side. The output was bit-identical to the uncached run, which is the only evidence I accept that I understood the cache and not only the speedup.

That is also where the honest accounting stops. Nothing here is optimized: no batching, no SIMD, no quantization. The context length is a constant in the source, set to 1,024 tokens.

A Few Distractions

Reading the HuggingFace files directly, with no Python anywhere in the pipeline, meant opening three things I had used for years without looking inside.

The checkpoint format. A safetensors file is an 8-byte header length, a JSON header mapping tensor names to offsets, then raw bytes. So the engine needed a JSON parser, which is 250 lines of BASIC and reads the 2 MB tokenizer.json in 70 ms. The weights are bf16, and a bf16 is the top 16 bits of an fp32, so converting one is a 16-bit shift. I had read that sentence before. Writing the shift is when I believed it.

The rotary convention. HuggingFace applies rotary position embeddings to the pair (j, j + head_dim/2) within a head. llama2.c rotates adjacent pairs. Rather than write a second RoPE, the loader permutes the rows of the query and key projections as it converts them, so the BASIC RoPE stays line for line with run.c. Attention scores are dot products per head, and a permutation applied to both sides leaves them unchanged, so every logit stays identical. A tutorial skips this detail. A checkpoint does not.

The tokenizer. The vocabulary in tokenizer.json is written in GPT-2’s byte-level alphabet, where a space shows up as Ġ, so the loader has to map it back to raw bytes. QB64 has no regular expressions, so the GPT-2 pre-tokenizer pattern became a hand-written scanner with Unicode letter, digit, and whitespace tables. The result matches HuggingFace on 2,060 test strings, CJK included.

Try It

docker run -it bmuskalla/gotoken

The image is 370 MB, built for amd64 and arm64, and holds only the binary and the model. Type a prompt, get a continuation, one token per second. /temp 0 makes it greedy and deterministic. At 0.7 the model tells a different story each time, and above 1.2 it falls apart. It is a base model, so it continues text rather than answering. Source and oracle are on GitHub.

Lessons Learned

An inference engine is easy in the basic form, especially when you have something to compare it to. Embedding, norm, attention, feed-forward, sampler: each is a short loop, and the oracle tells you within seconds whether the loop is right. The hard parts start when you optimize. The KV cache was the first taste of that. Batching, real kernels, and quantization are where the engineering lives, and none of them is in this repository.

Do we need another inference engine? No. vLLM is great, and so are the others. But building one from scratch gave me a mental model I did not have from reading, and that model is what I will use to make better decisions about the off-the-shelf engines I run from here on. And it was a lot of fun to go back to the old days of QBasic and bring them into this era.
